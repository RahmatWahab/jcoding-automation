## Priority findings

1. **I-01 High: goal is a mutable map, not a governed lifecycle.** `GoalContract.java:94-142` puts status ACTIVE/NEEDS_CLARIFICATION in a map; `WorkflowStateCodec.java:66-89` types only five control fields; `StateStore.java:280-321` saves arbitrary map state without transition validation. Scenario: a stale caller can persist an ACTIVE goal after cancellation or a requirement edit; state format alone cannot reject it. **Recommended:** versioned `IntentInstance` with explicit allowed transitions and a persisted event/revision guard. Confidence high, code verified; scenario not executed.
2. **I-02 High: changed requirement detection is broad but shallow.** `GoalContract.java:140,145-160` hashes the entire goal plus epic body; the hash includes derived fields, controller permissions, and selection details. Any textual or policy change invalidates all plan/ledger progress, while semantic contradictions between an earlier request and a new comment are not resolved. Scenario: a harmless issue formatting edit causes a full replan; a conflicting clarification can replace structured contract fields without explicit conflict review. **Recommended:** separate source revision, normalized requirement identifiers/provenance, and policy revision; diff them before invalidating affected tasks. Confidence high, code verified.
3. **I-03 High: acceptance coverage can be vacuous.** `GoalContract.java:91-93` only requires criteria when configured. `TaskPlan.java:67-84` demands each task map to criteria, so planning blocks when no criteria; when planning is disabled the empty goal may proceed. Scenario: a story lacking criteria reaches implementation with no measurable outcome when `require_acceptance_criteria=false` and `enable_planning=false`. **Recommended:** require at least one testable outcome or record explicit human approved exception, and use same gate regardless of planning mode. Confidence high, exact end-to-end scenario unverified.
4. **I-04 Medium: plan/task evidence may become stale across code changes.** `TaskLedger.java:20-43` can carry forward VERIFIED tasks if definitions and dependencies match; it does not check code/head or verification-policy hash in the preserved evidence. `TaskPlan.java:23-27` binds base SHA but not current head at every task transition. Scenario: later task changes code that invalidates earlier verified behavior; ledger still reports complete. **Recommended:** bind per-task proof to HEAD/tree fingerprint and checks policy; invalidate affected/downstream proofs after edits and run final full verification. Confidence high, code verified.
5. **I-05 Medium: clarification trust is coarse.** `ClarificationReply.java:12,23-39` accepts GitHub OWNER/MEMBER/COLLABORATOR association and a 16-character hash marker, picking latest by creation timestamp. It does not bind to a specific requester/approved principal or enforce what fields a reply may change. Scenario: any collaborator who can comment posts a marked JSON answer that changes intent/constraints. **Recommended:** explicit authorized principals or policy role and a proposal ID, immutable original objective, conflict review for scope/risk changes. Confidence high, code verified.
6. **I-06 Medium: concurrent state updates risk lost work.** `StateStore.java:290-305` increments a version inside a transaction but performs unconditional upsert from a caller-owned map; no expected-version predicate. Scenario: two controllers load the same state and each saves; last writer overwrites the other's goal/ledger changes. **Recommended:** single-controller lease plus optimistic revision compare-and-swap for every update. Confidence high, code verified; concurrency scenario not run.
7. **I-07 Medium: recovery decisions rely on worker-formatted fields.** `StateRecovery.java:41-69,140-212` parses the last matching text lines, checks enums/evidence literal, then changes phase. It does not require a structured decision bound to goal revision, HEAD, and observed evidence. Scenario: worker output embeds a misleading valid footer, directing resume despite stale goal. **Recommended:** structured schema validated against current snapshot and controller-observed facts. Confidence high, code verified.

## Small target intent/state model

Extend the current SQLite-backed store rather than add a service. Persist `IntentInstance {id, story, source_revision, goal_revision, objective, requirements[{id,text,source,priority,status}], constraints[{id,text,source,enforcement}], assumptions, non_goals, criteria[{id,text,check_ids}], authorized_actions, status, plan_revision, current_head, created_at, updated_at}`. Track `PENDING_CLARIFICATION → ACTIVE → PAUSED/BLOCKED → VERIFYING → VERIFIED/FAILED/CANCELLED/SUPERSEDED` with deterministic transition checks and event records. Each task stores dependency IDs, requirement IDs, attempt budget, current status, and evidence bound to goal revision, HEAD/tree fingerprint, check-policy hash, and tool output reference. On issue/reply edits, perform a requirement-level diff, mark conflicts for clarification, invalidate only proofs affected by changed requirements or code, and always rerun final acceptance checks. Use `StateStore` transactions with expected revision, retain `EffectJournal` for consequential effects, and make all actor decisions carry provenance and authorization. Tests should cover stale saves, conflicting amendments, cancellation at action boundary, proof invalidation after later edits, process restart, and ambiguous external effect reconciliation.
